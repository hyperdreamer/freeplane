## 1. Background

`GraphWorkspaceWindowModel.createContent()` (`GraphWorkspaceWindow.java:1036-1047`) builds the
window body as one `BorderLayout`:

```java
graphArea.add(mapList, BorderLayout.WEST);           // Maps sidebar
graphArea.add(graphScrollPane, BorderLayout.CENTER); // canvas
graphArea.add(settingsPanel, BorderLayout.EAST);     // Display settings
```

The Maps sidebar (`MapListPanel`) is therefore fixed at its preferred width: `PANEL_WIDTH = 264`
(`MapListPanel.java:40`) is applied as the panel's preferred **and minimum** size
(`MapListPanel.java:196-197`), as the preferred size of both lists
(`MapListPanel.java:336-337`) and as the cell renderer's cell width
(`MapListPanel.java:594`). There is no per-workspace width, and the panel cannot be hidden.

The right-hand Display panel is the established precedent for a hideable panel: the toolbar gear
and `View → Settings` both route through `GraphWorkspaceWindowModel.toggleSettingsPanel()`
(`GraphWorkspaceWindow.java:987-990`), which flips `settingsPanel.setVisible(...)` and mirrors the
state on the toggle. Its width is fixed at 244 (`WorkspaceSettingsPanel.java:26`) and stays as
shipped.

Per-workspace presentation state is already persisted: `DisplaySettings`
(`show-arrowheads`, `canvas-theme`, `remember-viewport`, `dim-unrelated-nodes`) is written into the
workspace XML `display-settings` element by `WorkspaceXmlCodec.displaySettingsXml`
(`WorkspaceXmlCodec.java:565-577`), parsed by `parseDisplaySettings`
(`WorkspaceXmlCodec.java:308-319`), and changed through the undoable workspace command path
`GraphCommands.display(...)` (`GraphCommands.java:94`) → `WorkspaceCommands.setDisplaySettings(...)`
(`GraphCommandRouter.java:110-112`). Unknown attributes inside `display-settings` are recorded and
re-emitted (`recordUnknownXml`, `WorkspaceXmlCodec.java:327-330`), the file format's
forward-compatibility mechanism.

## 2. Goals

1. The Maps sidebar width is adjustable by dragging a divider on its right edge, with the
   standard split-pane affordances and no custom divider painting.
2. The sidebar can be hidden and restored from three places: a chevron in the *Maps* heading, a
   slim rail that remains while hidden, and a checkable `View → Maps sidebar` item whose checked
   state always reflects the current layout.
3. Width and hidden state persist per workspace and travel with the workspace file, with no
   format-version bump and no loss of unknown XML from other builds.
4. Everything in the sidebar keeps working while it is hidden: the *Maps* menu remains the full
   action surface, and the rail carries the active-map count.
5. One layout gesture produces at most one workspace mutation, and programmatic re-application
   never produces one.
6. The right Display panel keeps its shipped appearance and behaviour; only its settings
   pass-through line changes (see 5.1).

## 3. Non-Goals

- Resizing or restyling the right Display panel; giving it a drag divider.
- Moving, docking, floating or re-ordering the Maps sidebar (left edge only).
- Animating collapse/expand.
- A toolbar toggle button for the sidebar.
- Persisting layout in Freeplane preferences (global) or per session only.
- Changing `MapListPanel`'s row content, ordering, selection model, or the map actions.
- A format-version bump or a `WorkspaceMigration` for this change.

## 4. User-facing behaviour

### 4.1 States

| State | Layout | Controls |
| --- | --- | --- |
| **Expanded** | sidebar visible, width = effective width clamped to the bounds below | chevron `◀` button at the trailing edge of the *Maps* heading, tooltip `Hide maps sidebar` |
| **Collapsed** | rail only, 26 px wide | rail chevron `▶` button, tooltip `Show maps sidebar`; vertical `MAPS` label; active-map count badge |

- Default width 264 px; allowed width `MIN_WIDTH = 180` … `maximumWidth(splitWidth)`, where
  `maximumWidth(splitWidth) = max(180, splitWidth / 2)`. For a 1000 px graph area the range is
  180…500.
- **Every committed width is inside those bounds**: the commit path clamps first, so no gesture
  can persist a value outside the range, and the interactive drag ceiling is the same number
  (4.3).
- A pre-existing stored value outside the range (written by a build with different bounds, or by
  hand) is displayed clamped and **preserved**; it is not rewritten until a gesture changes the
  displayed width, so opening a workspace in a small window never destroys the stored preference.
- Narrow graph areas: the sidebar's minimum is
  `effectiveMinimum(splitWidth, effectiveDividerWidth, insets)`
  (6.1) — normally 180 px, shrinking to the space that actually fits when the graph area is too
  small to hold it. Every clamp input is the divider component's laid-out width rather than the
  logical 6, so the sidebar's minimum, the canvas minimum and the L&F's own clamp describe the
  same geometry; see 4.3 for the three regimes that follow. Verified for FlatLaf 1×: the range is
  live from about 362 px of graph area upward, collapses to a single immobile position between
  roughly 186 and 361 px, and below the pinned threshold the sidebar shrinks with the window and
  **nothing is ever persisted**, so the stored width survives for a larger window. Documented
  degradation, not an error.
- Collapsing keeps the last expanded width; expanding returns to it (clamped to the current
  graph area).
- While collapsed the divider is locked: `setDividerSize(0)` and `setEnabled(false)`, so it
  cannot be grabbed and no resize cursor appears.
- Double-clicking the divider (expanded, gesture not in flight) resets the width to 264 px and
  commits it.
- `View → Maps sidebar` is a checkable item; checked means expanded; selecting it toggles the
  state. Its checked state is set in the single apply path (6.5), so chevron, rail, undo/redo and
  workspace open all agree. It stays enabled in every state, including read-only workspaces.
- Hiding the sidebar never disables a map action: `Maps` menu items keep their existing
  enablement rules (`updateMenuEnablement`, `GraphWorkspaceWindow.java:1009-1034`), computed from
  the map list regardless of visibility.

### 4.2 The collapsed rail

- Width 26 px, background and border from the current Look-and-Feel; no custom painting.
- Contents, top to bottom: the restore chevron button (18 px square, tooltip
  `Show maps sidebar`), the active-map count badge, the rotated label `MAPS`.
- Badge value = number of rows in the `ACTIVE` partition of the last `setRows(...)` call — the
  same number `activeHeader` shows as `ACTIVE (n)` when expanded; loading, retryable, missing and
  read-only rows all count because they live in the active partition
  (`GraphWorkspaceWindow.java:1200-1201`).
- Zero active maps ⇒ the badge is not painted (no `0` pill); the tooltip still reports the count.
- Badge tooltip: `graph_workspace.map_list.rail_count` formatted with the count. It is a single
  key with a bare numeral and no plural handling, matching the shipped `{0} nodes` counter
  (`graph_workspace.map_list.node_count`), which already renders `1 nodes`/`0 nodes`; the badge
  itself paints only the numeral, so this is a tooltip-only wording choice consistent with the
  rest of the window.
- The badge updates on every `setRows(...)`, so it stays correct while hidden.

### 4.3 Divider gesture protocol

Split pane configuration: `setContinuousLayout(true)`, `setDividerSize(6)`,
`setResizeWeight(0.0)`.

**Interactive clamping.** The L&F computes the draggable range from the two components' minimum
sizes; verified against JDK 21 and a headless probe (Metal and FlatLaf 3.7.2):

```
maxDividerLocation = splitWidth - rightMinimum - effectiveDividerWidth - insets.right
minDividerLocation = leftMinimum + insets.left
```

`effectiveDividerWidth` is the divider component's laid-out width
(`((BasicSplitPaneUI) splitPane.getUI()).getDivider().getDividerSize()`, which FlatLaf scales),
never the logical 6 passed to `setDividerSize`. **All clamp arithmetic in this design reads live
geometry from the split pane — effective divider width, insets, width — and none of it uses the
logical constants.** That contract is what makes the interactive ceiling exact at every L&F scale
and keeps the re-clamp convergent.

Dragging is disabled when the computed maximum is strictly less than the minimum (equality is a
valid, pinned drag range). The design therefore sets:

- `MapSidebarPanel` minimum = `effectiveMinimum(splitWidth, effectiveDividerWidth, insets)` while
  expanded (26 while collapsed), so the sidebar minimum is always a value the L&F can honour and
  the clamp below always has a fixed point, and
- the **right component's** minimum — that is `graphScrollPane`, not the inner `GraphCanvas`
  (whose own 320 px minimum is unrelated and stays) — to
  `MapSidebarLayout.canvasMinimumWidth(splitWidth, effectiveDividerWidth, insets)`, derived so that
  `maxDividerLocation == maximumWidth(splitWidth)` whenever that value is positive.

`canvasMinimumWidth` is recomputed whenever the split pane is resized, the divider width changes,
or the L&F scale changes. Measured on FlatLaf 3.7.2 at `uiScale` 1, 2 and 3 with the effective
divider width, `getMaximumDividerLocation()` equals `maximumWidth(splitWidth)` exactly, and a
re-clamp listener converges in a single pass (zero further listener re-sets per layout pass).
Feeding the logical 6 instead would yield 494 at `uiScale=2` and 488 at `uiScale=3` and would leave
one listener re-set per layout pass in the squeezed regime — the round-3/round-4 fixed-point
finding — so the live width is a contract, not an optimisation.

**Three regimes**, all derived from the formulas above:

| Regime | Condition | Divider | Width commits |
| --- | --- | --- | --- |
| Normal | `maximumWidth > effectiveMinimum` | live range `effectiveMinimum … maximumWidth` | allowed |
| Pinned | `maximumWidth == effectiveMinimum` (i.e. the range collapses at `MIN_WIDTH`) | immobile | allowed; they can only restate `MIN_WIDTH` |
| Squeezed | `effectiveMinimum < MIN_WIDTH` | immobile; the sidebar shrinks with the window | **suppressed** — nothing is persisted and the stored width is preserved |

**Programmatic and keyboard moves are not clamped by the L&F.** `setDividerLocation(int)` stores
its argument verbatim, and the L&F keyboard actions include `HOME`/`END` (`selectMin`/`selectMax`)
which move the divider outside the component minimums. The design therefore re-clamps in one
place: a divider-location property listener that our own code did not cause re-applies
`clampWidth(location, splitWidth, effectiveDividerWidth, insets)` under the re-entrancy guard, so out-of-range values are never
displayed and never committed. In the squeezed regime the listener does not re-clamp at all (the
L&F pins the divider and the sidebar shrinks); re-clamping stays active in the normal and pinned
regimes, where our clamp and the L&F's describe the same geometry. Keyboard adjustments are not
gestures and are never deferred: each change is clamped as it arrives and committed when the split
pane loses focus.

**Commit triggers — one workspace mutation per gesture:**

1. mouse release on the divider component
   (`((BasicSplitPaneUI) splitPane.getUI()).getDivider()`, null-guarded), and
2. focus lost by the **split pane** — the L&F gates and executes keyboard divider resize from the
   split pane's focus handler, not the divider's, so the split pane is the component that can
   observe the end of a keyboard adjustment.

Both triggers read `splitPane.getDividerLocation()` and commit **only when it differs from
`appliedSidebarWidth`** — the width the apply path last set, which every programmatic apply
(open, undo/redo, resize, post-keyboard re-clamp) updates. That baseline is what makes a
press-and-release without movement, a focus loss without a keyboard adjustment, and a focus loss
that follows a programmatic apply all no-ops: none of them can rewrite a preserved out-of-range
stored width. The triggers additionally return early while collapsed and in the squeezed regime of
4.3, where the sidebar cannot reach `MIN_WIDTH`, so a below-minimum value can never be written and
the stored width always survives. A gesture that ends where it started produces no mutation
(`SetDisplaySettingsCommand` also no-ops on equal settings, `WorkspaceCommands.java:474-477`). The
focus-lost trigger is gated on `!sidebarGestureActive`, so one mouse gesture can never produce two
commits.

**Gesture invariants.**

- `sidebarGestureActive` is set on divider mouse press and cleared on release. A lost release
  (window deactivation mid-drag) is recovered on the next press or when the split pane loses
  focus, both of which clear the flag first. While it is set,
  `applySidebarSettings` is deferred so an unrelated canvas refresh cannot snap the divider, and
  the property listener does not re-clamp.
- While collapsed, the divider is **held** at `RAIL_WIDTH`: every location change our own code did
  not initiate is reset to `RAIL_WIDTH` under the guard (invisible, because the divider is
  zero-width), and both commit triggers return early. Collapse also clears `sidebarGestureActive`.
  A drag that began before the collapse therefore cannot widen the rail or commit a width.
- Programmatic divider moves (applying stored settings, window resize, post-keyboard re-clamp,
  the collapsed-state hold) are made under the re-entrancy guard and never commit.

## 5. Persistence, undo and read-only

### 5.1 Model and format

`DisplaySettings` gains two fields with getters, `equals`/`hashCode`/`toString` participation and
two new factory parameters:

- `int mapSidebarWidth()` — expanded width in pixels; the default constant is
  `DisplaySettings.DEFAULT_MAP_SIDEBAR_WIDTH = 264` (the model layer owns it, because
  `MapSidebarLayout` is package-private in the window layer and cannot be referenced from
  `org.freeplane.plugin.graph.workspace.model`).
- `boolean mapSidebarHidden()` — default `false`.

`DisplaySettings.defaults()` (`DisplaySettings.java:29`) and the private constructor gain both
fields, so that every `DisplaySettings.defaults()` caller (`WorkspaceDocument.java:77,270`,
`GraphWorkspacePresentation.java:33`, `GraphWorkspaceViewBinding.java:18`, and the tests) keeps
compiling with the same defaults and no second copy of 264.

The factory keeps its single explicit form: `DisplaySettings.of(boolean, CanvasTheme, boolean,
boolean, int, boolean, List<UnknownXml>)`. **No compatibility overload** is added (repository
Legacy Removal Policy). Every `DisplaySettings.of(...)` call site — 15 in 10 files, verified by
grep in review rounds 1–2, plus the declaration in `DisplaySettings.java:34` — is updated:
main `WorkspaceSettingsPanel.java:149`, `WorkspaceXmlCodec.java:312`; tests
`GeneratedWorkspace.java:411`, `GraphWorkspaceWindowModelShould.java:1204,1224,1226,1264`,
`WorkspaceCommandsShould.java:456`, `WorkspaceXmlCodecShould.java:236`,
`WorkspaceHistoryShould.java:110,161,181`, `GraphCommandRouterShould.java:165`,
`GraphWorkspacePresentationShould.java:29`, `GraphWorkspaceModelAcceptanceShould.java:184`.

`WorkspaceSettingsPanel.publishSettings()` (`:145-152`) must pass the **current**
`settings.mapSidebarWidth()` and `settings.mapSidebarHidden()` through instead of rebuilding a
default object; the panel otherwise stays as shipped. Without that pass-through, toggling any
Display checkbox would silently reset the sidebar to 264/expanded. A regression test pins it
(§9.5).

`display-settings` gains two **optional** attributes:

```xml
<display-settings show-arrowheads="true" canvas-theme="FOLLOW_FREEPLANE"
                  remember-viewport="true" dim-unrelated-nodes="true"
                  map-sidebar-width="264" map-sidebar-hidden="false">
```

- Decoding uses `element.hasAttribute(name)`: absent attributes take the defaults, so workspace
  files written by earlier builds load unchanged and `CURRENT_FORMAT_VERSION` stays `1`.
- `map-sidebar-width` present but empty, non-numeric, or `<= 0` is `malformed(...)`;
  `map-sidebar-hidden` uses the existing `booleanValue(...)` helper and rejects anything other
  than `true`/`false`.
- A valid integer outside the allowed range is clamped for display only and is **not** rewritten,
  so a workspace opened on a small window keeps the user's chosen width for a larger one.
- Both names are added to the `knownAttributes` array in `parseDisplaySettings` and to
  `attributes(...)` in `displaySettingsXml`, so they are never duplicated into unknown XML and
  unknown-XML round-tripping is otherwise untouched. The writer always emits them, which keeps
  round-trips byte-stable for files this build wrote; files from earlier builds gain the two
  attributes on their next save.

### 5.2 Undo semantics (decision)

Width and hidden changes reuse the existing undoable display-settings path
(`GraphCommands.display(newSettings)`) and participate in `WorkspaceHistory` exactly like
`show-arrowheads` or `canvas-theme`.

Rationale: `SetDisplaySettingsCommand` captures and restores the whole immutable
`DisplaySettings` object (`WorkspaceCommands.java:464-478`). A second, non-undoable mutation path
for the same element (viewport-style `GraphWorkspaceStore.updateViewport`,
`GraphWorkspaceStore.java:141-165`) would make a later undo of any display setting silently
revert the sidebar width or hidden flag captured in the older snapshot. One path, one snapshot
semantics. The commit protocol in 4.3 keeps a gesture to a single entry.

Rejected alternatives: (a) viewport-style non-undoable persistence — the snapshot conflict above;
(b) a separate XML element for layout — larger format surface for two integers, and it splits
"display settings" across two elements.

### 5.3 Read-only workspaces and the session overlay

Read-only bindings (`DefaultGraphWorkspaceController.isReadOnly()`, `:668-670`) reject every
mutation, and `WorkspaceXmlCodec` refuses to write such documents at all (`:84-90`). Approved
decision 6 requires resize and hide to stay usable there, session-only.

The window therefore owns a small session overlay:

- `Integer sessionSidebarWidth` and `Boolean sessionSidebarHidden`, both initially `null`.
- Every user gesture writes the overlay and then, **only when the binding is writable**, commits
  the same value through `GraphCommands.display(...)`. Read-only ⇒ zero commands.
- `applySidebarSettings` uses `sessionSidebarWidth`/`sessionSidebarHidden` when they are set and
  the binding is read-only, and the stored values otherwise, so an unrelated canvas refresh or
  window resize cannot revert a session interaction (the bug the review flagged).
- The overlay is cleared when the binding becomes writable or the window is re-bound to another
  workspace; stored values then win.
- `View → Maps sidebar` and both chevrons stay enabled, and the badge keeps updating.

### 6.1 `MapSidebarLayout` (new, package-private, window package, no Swing)

```java
static final int DEFAULT_WIDTH = DisplaySettings.DEFAULT_MAP_SIDEBAR_WIDTH; // 264
static final int MIN_WIDTH = 180;
static final int RAIL_WIDTH = 26;

static int maximumWidth(int splitWidth);                    // max(MIN_WIDTH, splitWidth / 2)
static int effectiveMinimum(int splitWidth, int effectiveDividerWidth, Insets insets);
// max(0, min(MIN_WIDTH, splitWidth - effectiveDividerWidth - insets.left - insets.right))
static int clampWidth(int requestedWidth, int splitWidth, int effectiveDividerWidth, Insets insets);
// effectiveMinimum .. max(effectiveMinimum, maximumWidth)
static int canvasMinimumWidth(int splitWidth, int effectiveDividerWidth, Insets insets);
// max(0, splitWidth - effectiveDividerWidth - insets.right - max(effectiveMinimum, maximumWidth))
```

`DEFAULT_WIDTH` re-uses the model constant and `MapListPanel`'s initial preferred width is set
from the same constant, so the literal 264 exists once. `canvasMinimumWidth` is expressed in the
L&F's own terms (4.3): it reproduces `maximumWidth` as the interactive ceiling in the normal
regime, subject to the L&F's `max(minimumDividerLocation, …)` wrapper, as long as the arithmetic
is fed the effective laid-out divider width (never the logical constant). The committed value is
always clamped by `clampWidth`, whose range is never
empty (`effectiveMinimum <= max(effectiveMinimum, maximumWidth)`), which is exactly what gives the
re-clamp listener a fixed point in every regime. Units are pixels and all functions are pure, so
they are testable without a UI.

- Rotated `MAPS` label using `graph_workspace.map_list.rail_label`.
- `setActiveMapCount(int)` sets the numeral and the tooltip and is idempotent, so repeated row

### 6.3 `MapSidebarPanel` (new)

- State: `collapsed` and `readOnly` (the latter is a forwarding flag for the map list, not layout
  state; the earlier "owns exactly one piece of state" wording was wrong).
- API: `setCollapsed(boolean)`, `isCollapsed()`, `setActiveMapCount(int)`, `setReadOnly(boolean)`,
  `mapList()`, `rail()`, `collapseButton()` (test accessors in the style of
  `MapListPanel.addButton()`).
- `setCollapsed` is **idempotent**: it returns immediately when the value is unchanged, so it
  cannot re-enter its own listener. Otherwise it shows exactly one of rail/list, recomputes its
  preferred and minimum sizes (expanded: preferred `DEFAULT_WIDTH` / minimum
  `effectiveMinimum(splitWidth, effectiveDividerWidth, insets)`; collapsed:
  preferred and minimum `RAIL_WIDTH`), and notifies a single `CollapsedListener`.
- The listener is invoked only for real changes; the window guards its own `setSidebarCollapsed`
  entry point (6.5), so neither the user path nor the programmatic path can recurse.

### 6.4 `MapListPanel` changes

- Heading row: the `NORTH` component becomes a `JPanel(BorderLayout)` holding the existing heading
  label (`WEST`) and an icon-only collapse button (`EAST`, name
  `graph-workspace-map-sidebar-collapse`, tooltip `graph_workspace.map_list.collapse`), exposed as
  `collapseButton()`; the window supplies the action. `GraphWorkspaceWindowModelShould.java:196`
  asserts the old direct child and is updated with it.
- Fixed-width assumptions are removed so the panel tracks the divider:
  - `setPreferredSize` keeps 264 px as the initial preferred width (it seeds the first divider
    layout); `setMinimumSize` becomes `(0, 0)`, because `BorderLayout` propagates child minimums
    upward and the real minimum belongs to `MapSidebarPanel`.
  - The lists' preferred sizes are set to the panel's current content width on every
    `setRows(...)` and again from a `ComponentListener` on `MapSidebarPanel`, so a sidebar
    resized without a subsequent `setRows(...)` does not keep stale list widths.
  - `RowRenderer` (a `static` class, `MapListPanel.java:556`) receives the list in
    `getListCellRendererComponent` and derives the cell width from `list.getWidth()` instead of
    `PANEL_WIDTH - 24`, so a wider sidebar paints full-width rows and selection highlight
    (regression: today's constant leaves an unpainted strip at 400 px).
- No change to row content, partitions, selection, actions, or `ROW_HEIGHT`.

### 6.5 `GraphWorkspaceWindowModel` wiring

- `createContent()` puts the split pane in `CENTER` and keeps `settingsPanel` in `EAST`.
  Component names: split pane `graph-workspace-split`.
- Construction order: the sidebar panel is created before `createContent()` (next to
  `mapList = new MapListPanel(...)`, `GraphWorkspaceWindow.java:443`), the collapse listener is
  `this::setSidebarCollapsed`, and the button is wired where the other map actions are wired
  (the maps menu items, `GraphWorkspaceWindow.java:1095-1113`).
- `View → Maps sidebar`: a checkable `JCheckBoxMenuItem` named
  `graph-workspace-maps-sidebar-menu-item`, created next to `viewSettingsMenuItem`
  (`GraphWorkspaceWindow.java:1093-1095`), whose action calls `setSidebarCollapsed(!collapsed)`.
- **One apply path.** `applySidebarSettings(DisplaySettings settings)` is the only code that
  reads stored/session state and the only writer of the `appliedSidebarWidth` field used as the
  commit baseline (4.3):
  1. compute effective hidden = `sessionSidebarHidden ?: settings.mapSidebarHidden()`, effective
     width = `sessionSidebarWidth ?: settings.mapSidebarWidth()` (only while read-only, per 5.3);
  2. if a gesture is active, defer (remember that an apply is pending and run it on release);
  3. set the guard; recompute `sidebar`'s effective minimum via
     `MapSidebarLayout.effectiveMinimum(splitWidth, effectiveDividerWidth, insets)`;
     `sidebar.setCollapsed(hidden)`; `splitPane.setDividerSize(hidden ? 0 : 6)`;
     `splitPane.setEnabled(!hidden)`; `splitPane.setDividerLocation(hidden ? RAIL_WIDTH :
     clampWidth(effectiveWidth, splitWidth, effectiveDividerWidth, insets))`; sync
     `mapsSidebarMenuItem.setSelected(!hidden)`;
     record `appliedSidebarWidth` (the clamped width, or `RAIL_WIDTH` while collapsed);
     refresh `canvasMinimumWidth`; clear the guard.
  It is called from `applyPresentation(...)` (`GraphWorkspaceWindow.java:557-571`) and from the
  split pane's `ComponentListener`.
- **Three guarded user entry points, all owned by the window:**
  - `setSidebarCollapsed(boolean collapsed)` — called by the heading chevron, the rail chevron
    and the View item. It wraps `panel.setCollapsed(...)` in the re-entrancy guard, so the
    listener cannot call back into it; writes the session overlay; commits
    `map-sidebar-hidden` when writable; then calls `applySidebarSettings` to place the divider
    (restoring the effective width on expand). The divider size and enabled flag are restored
    here as well — not only when collapsing (M8).
  - `commitSidebarWidth(int location)` — called by the two commit triggers. It returns early while
    collapsed and in the squeezed regime (6.1), compares the clamped location with
    `appliedSidebarWidth`, and otherwise writes the session overlay
    and commits `map-sidebar-width` when writable. Neither the stored value nor an L&F layout push
    is used as the baseline, and `appliedSidebarWidth` is refreshed by every programmatic apply.
  - `resetSidebarWidth()` — the divider double-click handler (§4.1). It runs under the same guard,
    writes the session overlay with `DEFAULT_WIDTH`, and commits `map-sidebar-width` when writable;
    while collapsed or squeezed it is a no-op.
- **Initial layout.** The constructor calls `applyPresentation(currentPresentation)`
  (`GraphWorkspaceWindow.java:507`) before `pack()` (`:147`), when the split pane has no size; a
  width applied then would clamp to 180. The window therefore records the pending effective width
  and performs the first real application once the split pane has a positive width (first
  `ComponentListener` callback), which is also what makes a stored width of e.g. 400 show as 400
  on open. A test pins that the initial divider location is the stored width, not 180.
- `updateMapRows(...)` (`GraphWorkspaceWindow.java:1171-1208`) additionally counts
  `MapPartition.ACTIVE` rows from the same list it hands to `mapList.setRows(rows)` (`:1207`) and
  calls `sidebar.setActiveMapCount(count)`.
- `setReadOnlyOnEdt` (`:992-1007`) forwards the flag to the sidebar panel (which forwards it to
  the map list) and clears the session overlay when the binding becomes writable.
- The split pane's `ComponentListener` refreshes `canvasMinimumWidth`, re-applies the effective
  width and, when it arrives, performs the deferred initial application.

## 7. Error handling and edge cases

| Case | Behaviour |
| --- | --- |
| Malformed `map-sidebar-width` (empty, non-integer, `<= 0`) | codec throws `malformed(...)`; the workspace is rejected like any other known-attribute violation |
| Malformed `map-sidebar-hidden` | `booleanValue(...)` rejects it |
| Valid but out-of-range stored width | displayed clamped; preserved until a gesture changes the displayed width, so a no-op gesture cannot rewrite it |
| Graph area in the squeezed regime (`effectiveMinimum < MIN_WIDTH`) | the sidebar shrinks with the window, the divider is immobile, **no commit** is possible (commit triggers and the double-click reset return early), and the stored width is preserved; the re-clamp has a fixed point, so no validation loop |
| Pinned regime (the range collapses at `MIN_WIDTH`) | divider immobile; a commit can only restate 180 |
| No-op gesture (press/release without movement, a focus loss without a keyboard adjustment, or a focus loss after a programmatic apply) | no command; the baseline is `appliedSidebarWidth`, so a preserved out-of-range stored width survives |
| Window resized while expanded | `canvasMinimumWidth` refreshed and the effective width re-applied under the guard; no mutation |
| Window resized while collapsed | divider held at `RAIL_WIDTH`, still disabled |
| Drag ends | exactly one `DisplaySettings` command, or none when the clamped value equals the displayed width |
| Keyboard adjustment (L&F arrows) | clamped on every change (never deferred) and committed once when the split pane loses focus |
| `HOME`/`END` L&F actions | re-clamped immediately by the property listener; never displayed or persisted out of range |
| Undo/redo of any display setting | the apply path restores the whole snapshot (width, hidden, other fields) and syncs the View item |
| Hide then reopen the workspace | collapsed state restored from `map-sidebar-hidden`; divider locked at the rail |
| Read-only workspace | controls usable, zero commands, session overlay keeps the interaction visible across refreshes and resizes; reopen restores the file's values |
| Read-only workspace + window resize | session width re-applied clamped; still zero commands |
| Zero active maps while collapsed | no badge; tooltip still reports the count |
| Collapse requested while a drag is in flight | the gesture flag is cleared and the divider is held at `RAIL_WIDTH`; both commit triggers return early, so the straddling gesture cannot widen the rail or commit a width |
| Canvas refresh arrives mid-drag | apply is deferred until the gesture ends, so the divider does not snap |
| Initial open | the first application waits for a positive split width, so the stored width (not the 180 px clamp) is shown |
| Workspace switch to a narrower window | stored width clamped on apply, not persisted |

## 8. Accessibility

- The divider keeps the Look-and-Feel's built-in behaviour, including its resize cursor, its
  `HOME`/`END` actions and the keyboard resize that FlatLaf gates on split-pane focus; the design
  adds no custom divider painting and does not make the divider non-focusable.
- Keyboard resize is observable because the commit trigger listens to split-pane focus loss, the
  component the L&F uses for keyboard divider resize.
- Both chevrons carry localized tooltips; the icon buttons get accessible names from the same
  keys through the existing `iconButton` path (it sets an accessible name when an icon resolves
  and falls back to text otherwise, `WorkspaceToolbar.java:382-405`).
- The rail label and the badge are labels rather than painted graphics; the badge tooltip states
  the count in words.
- The `View → Maps sidebar` checkable item is the keyboard-reachable toggle in every state and
  follows the menu conventions already used by `View → Settings`.

## 10. Risks

1. **Look-and-Feel divergence.** `JSplitPane` divider rendering and keyboard bindings vary by
   L&F (FlatLaf is production). The clamp arithmetic reads the split pane's live geometry — the
   effective laid-out divider width and insets — rather than the logical constants, which is what
   keeps the ceiling exact at `uiScale` 1–3 and the re-clamp convergent; cosmetics stay L&F-owned
   by design.
2. **Stale fixed-width code.** Remaining `PANEL_WIDTH` use in `MapListPanel` would surface as
   partially painted rows or clipped lists; §9.4 pins this down.
3. **Undo noise.** A gesture ending at the current value must not create an entry; the commit
   protocol and the command's equality check cover it, and §9.5 asserts it.
4. **Hidden-state drift.** Divider position, collapsed flag and the View item's checked state
   could desynchronize if more than one path applied them; §6.5 keeps exactly one guarded apply
   path plus three guarded user entry points (`setSidebarCollapsed`, `commitSidebarWidth`,
   `resetSidebarWidth`).
